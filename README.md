# MPS · Menu Portal Solution

**주방 운영(Kitchen Control) 시스템.** POS가 주방프린터로 보내던 주문 정보를 화면(KDS)으로 받아 주방 파트(스테이션)별로 전송하고, 조리 → 완료 → 서빙까지 하나의 흐름으로 관리합니다.
본부의 표준 레시피와 표준 조리시간을 모든 가맹점에 똑같이 적용하고, 조리시간과 지연을 측정해 **음식 품질과 고객 서비스**를 관리합니다.

```
 POS ──(주방프린터 출력)──▶ 프린터 브릿지 에이전트 ──▶ MPS 서버 ──(실시간)──▶ 스테이션 KDS (그릴/국·찌개/튀김/찬/음료)
  └──(POS API 연동, 선택)─────────────────────────▶   │                         │ 품목 조리·완료(BUMP)
                                                     │                         ▼
                                                     └──────────────────▶ 패스(Expo) KDS ── 서빙 완료
                                                     │
                                       본부·지점·매장 관리 포털 (메뉴·레시피·스테이션·사용자·품질 분석)
```

## MENU PORTAL · Kitchen Control System

모든 주문을 한 화면에서 **테이블 단위**로 관리하는 메인 운영 화면입니다 (`/portal`).

| 영역 | 내용 |
|---|---|
| 01 주문 통합 수집 | POS, 테이블오더, 주방프린터 전표, **직원 호출·고객 요청**을 한 화면으로 수집 |
| 02 주문서 관리 | 테이블 카드: 테이블 번호·주문 시각·인원·유입경로, 메뉴별 상태 칩과 경과시간, 하단 5버튼(호출/대기/조리중/완료/취소), 탭(전체/대기/호출/조리중/완료/취소)·검색·카드/목록 보기 |
| 03 테이블별 메뉴 관리 | 카드 ⋮ → 테이블의 전체 메뉴 구성과 상태 |
| 04 메뉴별 진행 관리 | **진행 수량(1/2 일부완료)** 조정, 조리시간 vs **기준 범위(예: 4~6분)**, 표준 레시피, **조리 진행 이력(시간·상태·수량·작업자)** |

조리 상태: `대기 → 조리중 → 일부완료 → 호출(조리완료·홀 픽업 호출) → 완료(제공)`, 그리고 `부분취소`(수량 일부) / `취소`.
상태 칩을 누르면 다음 단계로 진행하고, 행을 선택한 뒤 하단 버튼으로 원하는 상태를 직접 지정합니다. 취소·부분취소는 매니저 이상만 할 수 있으며 사유가 기록됩니다.

모든 상태 변경은 `order_item_events`에 **시각·수량·작업자·사유**와 함께 쌓이고, 이 데이터로 9개 영역을 분석합니다 (관리 포털 → 운영 품질 분석).

| 분석 영역 | 지표 |
|---|---|
| ① 속도 | 조리 착수 대기, 첫 메뉴 제공, 전체 조리완료, **테이블 동시제공 편차**, **픽업 대기(호출→제공)**, 스테이션별 |
| ② 품질·표준 | 메뉴별 기준시간 범위 준수: **과속**(하한 미만)·지연(상한 초과), 조리시간 편차 |
| ③ 정확도·손실 | 메뉴별 취소 수량, **조리 시작 후 취소(손실)**, 취소 사유 |
| ④ 메뉴 | 판매량, 주방 점유(수량×조리시간), **함께 주문되는 조합** |
| ⑤ 테이블·고객 | 인원별 주문 수·인원당 메뉴 수·체류시간 |
| ⑥ 인력 | 작업자별 조리·제공 수량, 평균 조리, 지연율, 되돌림, 취소 처리 |
| ⑦ 수요 | 요일×시간대 히트맵, 시간대별 주문·조리시간 |
| ⑧ 유입·요청 | POS/테이블오더/프린터별 주문·취소율, 직원 호출·고객 요청 유형별 응답·처리 시간 |
| ⑨ 매장 비교 | 가맹점별 조리완료·패스 대기·초과율·취소율 |

## 빠른 시작 (로컬 개발)

필요: Node.js 22+, PostgreSQL 16

```bash
# 1) DB 준비
createuser -s mps && createdb -O mps mps && psql -c "ALTER USER mps PASSWORD 'mps'"

# 2) 설치 + 데모 데이터
npm run install:all
npm run seed            # 스키마 초기화 + 데모 조직/계정/메뉴/7일치 주문

# 3) 실행 (터미널 2개)
npm run dev:server      # http://localhost:4000  (API + Socket.IO)
npm run dev:web         # http://localhost:5173  (관리 포털 / KDS)
```

데모 계정 (개발 모드 로그인 화면에 버튼으로 표시)

| 가맹본부 | `hq` / `hq1234` |

## 운영 배포 (Docker)

```bash

docker compose up -d --build
docker compose exec app node src/db/seed.js     # (선택) 데모 데이터
```

## 매장 연결: POS를 고치지 않는 방법

1. 관리 포털 → **POS · 프린터 연결** → 연결 키 발급(유형: 프린터 브릿지)
2. 매장 PC에서 에이전트 실행
   ```bash
   MPS_SERVER=https://mps.example.com MPS_DEVICE_KEY=mps_xxx \
   FORWARD_PRINTER=192.168.0.50:9100 node agent/printer-agent.js
   ```
3. POS 설정에서 주방프린터 IP를 매장 PC 주소(포트 9100)로 변경

에이전트는 ESC/POS 원본을 서버로 보내고(서버가 제어 명령 제거 → CP949 디코딩 → 테이블/주문번호/메뉴/수량/옵션/요청사항/포장·배달/취소 전표 해석), `FORWARD_PRINTER`가 설정되면 실제 프린터로도 그대로 출력해 종이 백업을 유지합니다. 서버 장애 시 전표를 로컬에 저장했다가 재전송하며, 같은 전표의 중복 주문은 서버가 막습니다.
POS사가 API 연동을 지원하면 `POST /api/pos/orders`로 직접 보낼 수도 있습니다. **테이블오더** 단말은 연결 키 유형을 `테이블오더`로 발급하면 같은 API로 주문(인원 포함)과 직원 호출·고객 요청(`POST /api/pos/requests`)을 보냅니다 ([docs/API.md](docs/API.md)).

전표 해석 결과는 **POS 연동 · 테스트 → 주방프린터 전표 테스트**에서 미리 확인할 수 있습니다. 해석하지 못한 줄은 버리지 않고 `[미확인]` 메모로 주방에 그대로 보여 줍니다.

## 주방 흐름

1. 주문 수신 → 메뉴별 **조리 파트**로 자동 분배 (매장 재지정 > 본부 조리 파트 유형 > 기본 스테이션)
2. MENU PORTAL(테이블 단위) 또는 스테이션 KDS(파트 단위)에서 조리: 스테이션 화면은 품목 탭으로 `대기 → 조리중 → 호출`, **조리완료·호출** 버튼으로 티켓 일괄 처리, **리콜**로 되돌리기
   - 경과시간/표준시간 비율로 색상 표시 (70% 미만 초록, 70% 이상 주황, 초과 시 빨강 깜빡임), 긴급 주문 상단 고정
   - **레시피** 버튼으로 본부 표준 레시피 확인
3. 메뉴가 조리되면 **호출** 상태가 되어 홀이 가져가고 **완료**(제공) 처리 — 메뉴 단위(MENU PORTAL) 또는 주문 단위(패스 화면 **서빙 완료**)
4. 모든 상태 변경이 조리 진행 이력으로 기록되어 위 9개 영역 분석에 반영됩니다.
